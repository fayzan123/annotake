# Flipbook M2–M4 design: recording, output, and the rest of the app

> Written when the app was called Flipbook; it's Annotake since 2026-09-30 ([distribution design §3](2026-09-30-distribution-design.md#3-the-name-annotake)).

**Status:** approved 2026-09-24 · **Plan:** [2026-09-24-m2-m4-app.md](2026-09-24-m2-m4-app.md) · **Spec:** [../spec.md](../spec.md), updated with the changes in §11

Worked out with Fayzan in Session 3, on top of [the M0 findings](../spikes/findings.md) and the M1 code in `Sources/FlipbookCore`.

## 1. Goal

- **Scope:** M2–M4 from spec §10:
  - M2: Right ⌘ → capture → frames in a folder.
  - M3: caption strips, click markers, `steps.md`, the card, and filmstrip trimming.
  - M4: Settings with the Meet-style picker, first launch, the menu bar, retention cleanup, and sounds.
- **Done means:**
  - v1 is feature-complete per the spec,
  - `make test` passes,
  - the manual checklist (spec §8, split across the two checkpoints in §10 below) passes on both Macs.

  M5 dogfooding can then start.
- **Ease of use comes first.** The flow is: press the key, reproduce the bug, drag the card.
  - Nothing in M2–M4 may add a step, a confirmation, or a wait to that flow.
  - Defaults work with no setup.
  - Failures degrade instead of blocking a recording.
  - The recording state is always visible.
- **Constraints:**
  - Everything is built and tested on the personal MacBook (macOS 15.7, Command Line Tools 26.3, `make test`).
  - No network use and no AI.
  - The implementing agent can't press keys, grant permissions, or reach the work Mac.

## 2. Decisions

| Decision | Why |
|---|---|
| Two implementation sessions: Session 4 builds M2 + M3, Session 5 builds M4 | The recording loop gets real use at Checkpoint 1 before M4 is built on top of it, and each session stays a manageable size |
| A checkpoint only where Fayzan must act or give an opinion | Sessions run unattended. Tests, the self-test, and the log cover everything else |
| `LiveSession` in Core feeds the picker through one time-ordered queue | A click's label arrives up to ~100 ms after the click. Without ordering, a click can attach to its own result, and raw sessions wouldn't replay the way they ran live |
| Cursor rules: a change under a pointer that didn't move counts | After a click the pointer sits on what it clicked, so a ticked checkbox produced no frame, contradicting §5.3 |
| A hold released before the reveal is discarded | If the pill never appeared, nothing was recorded. This closes a gap where a 0.75–0.8 s hold saved a card with no feedback |
| `--selftest` records the app's own scripted window | Capturing its own windows needs no Screen Recording permission (`SCShareableContent.currentProcess`, macOS 14.4+). Unattended sessions can run the real pipeline and look at the output, with nothing personal in it |
| The app is a library (`FlipbookApp`) plus a one-file executable | Tests import a library the normal way, instead of relying on testable executables under the Command Line Tools |
| Clicks and scrolls outside the recorded area aren't logged | The frames can't show them |
| Click cleanup strips the trigger's own modifier | With Right ⌥ as the trigger, a hold-and-click would otherwise be an ⌥-click, and Chrome would download the link |
| First launch is one checklist window, and the menu gains "Fix permissions…" | A checklist takes fewer clicks than a wizard. Screen Recording expires monthly, so the fix stays one click away |
| Launch at login is only registered from an Applications folder | A development build in `build/` never leaves a stale login item |
| The pill ignores clicks while recording | It sits over the app being recorded |
| At most 4 cards are visible, and the filmstrip keeps at least one frame | Cards shouldn't fill the screen, and an empty capture is useless |
| `.raw/capture.json` holds what re-rendering needs | The filmstrip and Recent Captures must work after a relaunch. The file is internal, not the public machine-readable file the backlog defers |

## 3. Architecture

### 3.1 Targets

| Target | Uses | Holds |
|---|---|---|
| `FlipbookCore` | Foundation only | M1's code, plus `LiveSession`, `RawSessionWriter`, and the cursor rules |
| `FlipbookCapture` | ScreenCaptureKit, CoreVideo, CoreGraphics | target resolution, the content cache, filters and exclusions, the stream, frame → signature, output sizing, point mapping |
| `FlipbookInput` | CoreGraphics event taps, ApplicationServices (Accessibility), AppKit (`NSWorkspace`) | the input thread, taps, trigger keys, event classification, AX labels and flags, app/window context |
| `FlipbookExport` | CoreGraphics, CoreText, ImageIO | capture folders, rendering, writing PNGs and `steps.md`, filmstrip trims, retention |
| `FlipbookApp` | AppKit, SwiftUI, ServiceManagement | `SessionController`, the recording pipeline, the pill, card, filmstrip, menu, Settings, first launch, the self-test |
| `Flipbook` | — | `main.swift`, which calls into `FlipbookApp` |
| `flipbook-replay` | — | unchanged |

- Each library has its own test target (`FlipbookCaptureTests` …), and `make test` runs all of them.
- Core keeps its rule: Foundation only.

### 3.2 Threads

- **Main:** the UI, `SessionController`, and `NSWorkspace` notifications.
- **Input thread:** a dedicated thread with its own run loop. It hosts both event taps and the `GestureRecognizer`. The callbacks only classify events and hand them off, because macOS disables a tap whose callback is slow, and a busy main thread would otherwise delay every click on the Mac.
- **AX thread:** its own run loop, for label lookups, the focused field and window, AX observers, and the Chrome/Electron flags. A 0.25 s global AX messaging timeout keeps a hung app from stalling it.
- **Recording queue:** serial. ScreenCaptureKit delivers frames here, signatures are computed here, and `LiveSession` runs here with a 50 ms timer. This is spec §6.1's "Capture and Core on one serial queue".
- **Writer queue:** PNG encoding, both for `.raw` frames during recording and for rendered frames at export.

### 3.3 Data flow

```
Right ⌘ ─▶ Input thread (taps + GestureRecognizer) ─gesture─▶ SessionController (main)
              │ click / key / scroll / switch                     │ start / stop
              │   (click → reserve a slot; AX thread fills label) ▼
              └──────────────▶ Recording queue: LiveSession ◀── SCStream frames + signatures
                                    │ persist / discard / took
                                    ▼
               Writer: .raw/frame-<i>.png ──on finish──▶ Export: PNGs + steps.md ──▶ Card
```

### 3.4 `LiveSession`

`LiveSession` wraps `FramePicker`. It is the only way frames and events reach the picker, both live and in replay.

- **Timestamps.**
  - Each call carries a time in seconds since the recording started, taken when the item reaches the recording queue.
  - `LiveSession` keeps these times strictly increasing: a stamp equal to or earlier than the last one is moved 1 µs past it. So arrival order is time order.
- **Items.** Each item is a frame, an event, a slot, or stop. They all wait in one first-in-first-out queue.
- **Slots.**
  - Some events need an Accessibility lookup: a mouse-down, the first key of a typing run, an app or window switch, and the window title at start. Each of these reserves a slot that carries the unlabeled version of the event, and the AX thread fills it in.
  - Items behind an unfilled slot wait.
  - A slot that isn't filled within 0.5 s is released with its unlabeled version.
- **Ticks.**
  - Ticks fall on the replayer's grid, k × 0.05 s.
  - Before any item, every tick strictly earlier than that item runs.
  - The 50 ms timer runs ticks up to "now", but never past an unfilled slot.
- **Stop.**
  - Stop is an item too. When it's reached, ticks up to and including its time run, then the picker stops.
  - Frames keep flowing after stop until the picker has settled.
  - Input events stop at the gesture itself.
- **Outputs.**
  - Persist and discard, each with its logical time, and persist also with its keep reason, for the replay log.
  - "Took frame" and "took event": what the picker actually saw, in order.
  - The candidate count, for the pill.
- **Recording.** The pipeline writes the "took" outputs through `RawSessionWriter`. Signatures stream to `tiles.bin` as frames arrive, and `session.json` is written at the end, in `RawSessionIO`'s format.
- **Replay.**
  - `SessionReplayer` is rebuilt on `LiveSession`. It feeds the recorded items in by time, then stop at `stopTime`, then any frames after it, then ticks until the picker finishes.
  - Its public API doesn't change, and M1's replay, harness, and golden tests keep passing.
  - Recorded times are the effective stamps, and slot events carry their final labels, so replaying a raw session reproduces the live run exactly.

### 3.5 Core changes

1. **`LiveSession`, `RawSessionWriter`, and `SessionReplayer` rebuilt on them**, as in §3.4. A property test covers them together:
   - feed the click-flow scene live, with random label delays under 0.5 s and random timer calls;
   - the result must equal replaying the scene;
   - replaying what was recorded must give the same result again.
2. **Cursor rules** (spec §5.2 and §5.3):
   - `ChangeTracker` ignores the cursor's tiles only when the cursor rect differs between the two frames being compared. This applies both to motion detection and to D. If the cursor stayed put, its pixels are the same in both frames, so a change under it is real.
   - `FramePicker` keeps an *input baseline*: the latest frame at each mouse-down, at the first key of a typing run, at Return/Esc/shortcuts, and at a switch.
     - For a low-bar trigger (click, commit, switch, typing), the settled frame also clears the bar when it differs from that baseline by at least `minChangedTilesAfterInput` tiles.
     - This catches a checkbox ticked, or a digit typed, under a pointer that hasn't moved.
   - The golden fixture has no cursor, so it's unaffected. The existing cursor tests still hold, because their cursor moves.

Nothing else in Core changes.

## 4. Capture

**Target.** The `recordTarget` setting is one of three:
- the screen with the cursor (the default),
- a specific screen, stored by display UUID so it survives reboots,
- a window, stored by window ID and matched by ID only.

Capture handles all three from Session 4 on. The picker UI comes in Session 5.

**Starting a recording**
- Capture makes one fresh `SCShareableContent` query. It leaves out desktop windows and includes all other windows, not just on-screen ones, which also finds Notification Center on macOS 15. The query times out after 2 s.
- On timeout, Capture uses a cached copy, refreshed at launch and whenever the displays change. With no cache, the pill shows "Couldn't start recording — try again".
- Error −3801 shows "Screen Recording permission needed" with Open Settings. Nothing is saved.
- If the chosen window or screen is gone, Capture records the cursor's screen, and the pill says "Window not found — recording your screen" (or "Screen not found — …").

**Exclusions**
- **Display capture** excludes the Flipbook and `com.apple.notificationcenterui` applications. The pill is created at launch. Cards, the filmstrip, and Settings all belong to the app, so they're excluded too.
- **The menu-bar icon on macOS 26.**
  - At start, Capture looks for the status item's window in the content list: first by window number, then by its frame at menu-bar level.
  - If a different process owns that window, Capture excludes that app too and lists its other windows in `exceptingWindows`, so they stay visible. A filter can't exclude a single window of another app while also excluding whole apps.
  - The log records what was found.
  - If nothing matches, the icon stays in frames as a cosmetic issue, and the spec notes it. Checkpoint 2 verifies this on the work Mac.
- **Window capture** uses the `desktopIndependentWindow` filter. It follows the window across screens, with no desktop behind it and no shadow.

**Stream settings:** 10 fps (`minimumFrameInterval` 1/10), BGRA, cursor shown (`showsCursor`), queue depth 8, sRGB output color space, no audio. Window streams only scale down, never up.

**Output size.** A pure function, tested:
- Scale the source's pixel size so the long edge is at most 1920 px (1568 px in compact mode). Never scale up.
- Also keep the finished image, frame plus the tallest possible caption strip, within 2000 px on both sides. In practice only portrait windows hit this.
- Round to even numbers.
- `pixelsPerPoint` is the output width ÷ the source width in points.

**Each frame.** On the recording queue:
- Only `.complete` frames are used. Idle frames carry no image (M0).
- Dirty rects are already in output pixels with a top-left origin (M0). They're rounded outward into `PixelRect`s.
- **The signature.** A pure function over a pixel buffer, tested with synthetic buffers:
  - Each 8 × 8-pixel cell gets its mean brightness (integer luma weights).
  - 4 × 4 cells make one 32 px tile. Tiles are row-major, and so are the cells within each tile.
  - Row padding is handled.
  - An edge cell averages only the pixels it actually covers. Cells entirely beyond the image are 0.
  - Budget: under 8 ms for a 1920 × 1246 frame in a release build. The self-test measures it.
- **The cursor rect.**
  - Where the pointer is when the frame arrives, converted to output pixels.
  - It's a box from 12 pt above and left of the hotspot to 32 pt below and right of it, scaled by the Accessibility cursor-size setting.
  - It's nil when the pointer isn't over the target.
- **Point mapping.** A pure function, tested:
  - Screen mode subtracts the display's origin and scales.
  - Window mode uses each frame's `screenRect`, so moving or resizing the window mid-recording keeps click points correct.
  - Input uses the same mapping to drop clicks and scrolls outside the recorded area.

**Pixels**
- A small store keeps the pixel buffers of frames `LiveSession` hasn't taken yet, plus the latest one it took. That's usually 1–3 of the stream's 8.
- On `.persist(i)`, frame i's pixels are copied, and the writer queue encodes `.raw/frame-<i>.png` into the temp capture folder.
- On `.discard`, the files are deleted once any pending writes for them have finished.

**Failures mid-recording.** If the stream stops with an error (the window closed, the display was unplugged), `SessionController` stops and saves what was captured.

**Self-test source.** Capture can also take its window from `SCShareableContent.currentProcess` (§9).

## 5. Input

**Permissions.** Input Monitoring is checked with `CGPreflightListenEventAccess()`, never by whether tap creation succeeded (M0). Accessibility is checked with `AXIsProcessTrusted()`.

**Listen-only tap.** It lives on the input thread from launch and watches flag changes, key downs, mouse downs and ups, and scrolls. If macOS disables it, it's re-enabled.

**Trigger keys.** Detection is pure and tested with synthetic `CGEvent`s; creating an event needs no permission.

| Setting | Keycode | Counts as down when |
|---|---|---|
| Right ⌘ | 54 | device bit `0x10` is set |
| Right ⌥ | 61 | device bit `0x40` is set |
| fn / Globe | 63 | the secondary-fn flag is set |

Any other modifier going down is fed to the recognizer as `otherKeyDown`.

**Gestures**
- `GestureRecognizer` runs on the input thread, with `GestureConfig` taken from Settings.
- A 50 ms tick runs while the key is down, while recording, and for 1 s after a release. That covers every timed transition.
- Gesture events go to `SessionController`.
- When a recording ends some other way (the menu, auto-stop, an error), the recognizer gets `reset()`.

**Active tap.** It exists only while recording, and only with Accessibility. It's created on the input thread the moment `.startHold` or `.startHandsFree` fires, so no click slips through in between.
- In hold mode, it strips the trigger's modifier from mouse and scroll events: ⌘, or ⌥ when Right ⌥ is the trigger.
- Esc while the trigger is down is consumed, and the recognizer turns it into a cancel.
- A trust watchdog checks `AXIsProcessTrusted()` every 2 s and removes the tap if Accessibility has been revoked.
- It's added after the listen tap, so it sees events first. M0 confirmed the listen tap never saw the consumed Esc.

**Recording events.** Classification is pure and tested. Events are forwarded only while recording, and never after the stop gesture.
- **Keys:**
  - Return and keypad Enter → `keyReturn`.
  - Esc → `keyEscape`, unless it was consumed as a cancel.
  - Anything with ⌘ or ⌃ held → `shortcut(name)`. The modifiers come in Apple's order ⌃⌥⇧⌘, followed by the key as the current keyboard layout prints it, or its symbol: `⇧⌘T`, `⌃C`, `⌘↩`.
  - Printable keys, Space, Tab, and Delete → `keyTyped`. The character is never kept.
  - Arrows, navigation keys, and F-keys pressed alone aren't actions.
  - Auto-repeats add no actions.
- **Clicks:** left, right, and other buttons, with the click count. For a click outside the recorded area, both the down and its up are dropped. A mouse-down reserves a slot, and the AX thread fills in the label.
- **Scrolls:** dropped when the pointer is outside the recorded area. The fraction of the viewport is the point delta divided by the recorded area's height, because the scrolled view's own height isn't known.

**Accessibility.** On the AX thread, with the 0.25 s messaging timeout.
- **The label at a click point.** These are M0's rules, tested over a fake element tree:
  1. the element's title, then its description;
  2. static text inside a link or button takes the parent's label;
  3. a cell or row takes its first child's text (Finder file names);
  4. an unlabeled checkbox or switch takes its title element, or the text beside it in its row (System Settings);
  5. never read past a web area or window. A label found there counts as none, so the caption says `Clicked at (x, y)`.

  The role is the element's role description, lowercased. A secure text field's value is never read, anywhere.
- **The field for typing.** The first key of a typing run reserves a slot, and the focused field's label is looked up (title → description → placeholder), never its value. A new lookup happens after a click, a Tab, a switch, or a 1.2 s pause.
- **The Chrome/Electron flags** (M0 decision):
  - At start, set `AXEnhancedUserInterface` on Chrome, ignoring its −25208 error, and `AXManualAccessibility` on Electron apps (detected by `Electron Framework.framework`). The same goes for apps launched or activated during the recording.
  - At stop, clear the flags Flipbook set, unless VoiceOver is running.
  - Checkpoint 1 measures whether the first Chrome click after starting gets a label.

**Context**
- At start, the frontmost app's name is known immediately. Its window title comes through a reserved `titleChanged` slot at t = 0, so the first frame already has it.
- During recording, app activation reserves a `switched` slot.
- An AX observer on the frontmost app reports window changes (`switched`) and title changes (`titleChanged`). It moves to each newly activated app.
- Without Accessibility, captions get app names only, clicks stay unlabeled, and no flags are set (spec §7).

**Privacy.** Typed characters never leave the tap callback. Labels and titles only go into captions, `steps.md`, and raw sessions, never into the log file.

## 6. Export and the capture folder

```
~/Pictures/Flipbook/
  2026-09-23 at 14.05.12/
    01_0m00s.png …          rendered frames
    steps.md
    .flipbook               marker; holds the capture's date (ISO 8601), which retention reads
    .raw/
      capture.json          name, target, date, render options, picked frames, removed frames
      frame-000017.png …    unrendered picked frames, by frame index
      removed/              frames removed in the filmstrip
      session/              raw session, only with Advanced → Save raw sessions
  .flipbook-tmp/<id>/       captures being written
```

- The temp folder sits inside the save location, so the final move is a rename on the same volume.
- Leftovers from a crash are deleted at launch.
- If a folder name is already taken, the new capture gets " (2)", " (3)", and so on.
- `capture.json` is internal. It holds each picked frame's time, context, and actions for re-rendering, plus the counts and the duration for Recent Captures after a relaunch.

**Finishing.** Once the picker settles:
1. Delete the candidates that weren't picked.
2. Render the picked frames, at most 4 at a time.
3. Write `steps.md` (Core's text), `capture.json`, and `.flipbook`.
4. Move the folder into place. The card becomes draggable at this point.

The budget for 20 frames is about 0.3 s. The self-test measures it.

**Rendering.** CoreGraphics and CoreText, written as sRGB PNGs through ImageIO, and tested by output size and pixel probes.
- **The caption strip**, under the frame:
  - background `#1C1C1E`;
  - line 1 in semibold white at width ÷ 64 (30 px at 1920 wide, 24.5 px at 1568). It wraps to at most 3 lines and then ends with "…";
  - line 2 in regular `#A1A1A6` at 85% of that size, one line, truncated with "…";
  - padding is 0.8 × the line-1 size;
  - the strip grows with the number of wrapped lines. Its maximum is what §4's 2000 px budget reserves.
- **Click markers**, at each click point inside the frame:
  - a ring of radius width ÷ 80 (24 px at 1920 wide), drawn as 3 px of red `#FF3B30` over a 6 px white halo;
  - when a frame has several clicks, each ring gets a numbered red badge, in click order.
- The strip and marker toggles come from Settings. The options used are stored in `capture.json`, so later re-renders match the original.

**Filmstrip trims.** Tested. On close:
1. Core's `FrameEditing.removing` merges the removed frames' actions into their neighbors.
2. Each removed frame's `.raw/frame-<i>.png` moves to `.raw/removed/`.
3. Every remaining frame is re-rendered with its new number and total.
4. Rendered files that are no longer in the set are deleted.
5. `steps.md` and `capture.json` are rewritten. The "(from N candidates)" count stays the same.

**Retention.** Tested with a fake clock and a fake trash.
- At launch and every 24 h, every folder in the save location that contains `.flipbook` and is older than the setting (7 days, 30 days, or forever) goes to the Trash.
- Folders without the marker are never touched.

**Errors.** A write failure, such as a full disk, deletes the temp folder and shows the error card with "Show Folder". Nothing half-written reaches the captures folder.

## 7. App, part 1 (Session 4): recording, pill, card, filmstrip

**`SessionController`.** It runs on the main thread and is tested with fakes.
- **Start** happens on `.startHold`, `.startHandsFree`, or the menu's Start, which is hands-free.
  - It resolves the target, then starts capture, input recording, and a `LiveSession`.
  - A hold starts silently. Hands-free shows the pill and plays the start sound right away.
- **Reveal** comes at 800 ms: the pill appears and the start sound plays.
- **Discard or cancel** (a shortcut, or trigger + Esc): stop everything, delete the temp folder, hide the pill. No sound plays.
- **Stop** comes on release, a double-tap, the menu, or the 5-minute auto-stop.
  - A hold released before the reveal, or a hands-free recording under 0.5 s, is discarded silently.
  - Otherwise the stop sound plays, the pill hides, and **the card appears at once**, showing the duration and "Saving…".
  - The stream runs until the picker settles, which takes under 1 s. Then export runs, and the card fills in and becomes draggable, typically 0.7–1.3 s after the key is released.
- **The key is never blocked.** Settling and export run per capture in the background, so a new recording can start while the last one saves.
- **Errors** (spec §7):
  - The permission message shows even in hold mode, since nothing is being recorded.
  - A missing target falls back, with a note on the pill.
  - A stream error mid-recording stops and saves.
  - An export failure shows the error card.

**Pill.** A panel created at launch.
- It sits at the bottom center of the recorded screen, on every Space, including full-screen apps, as a dark capsule:
  - hold mode: `● 0:04 · 3 frames · release ⌘ to stop`
  - hands-free: `● 0:12 · 5 frames · double-tap ⌘ to stop · ⌘Esc cancels`
- The key glyph follows the chosen trigger.
- The frame count is capped at the frame limit, so the pill never promises more than the card will hold.
- It ignores mouse clicks while recording. It only takes clicks when it's showing a message with a button, such as Open Settings.
- Its text formatting is pure and tested.

**Card.** One panel per capture.
- It appears at the bottom right of the screen the cursor is on, with three stacked thumbnails and "8 frames · 0:21".
- It never takes focus and accepts the first click, so it drags straight into a chat without being clicked first.
- A drag drops every frame, in order. That's M0's proven payload.
- After a drop it fades out over about 5 s. Hovering over it stops the fade.
- ✕ (shown on hover) or a two-finger swipe right dismisses it.
- A click that moves less than 4 pt opens the filmstrip.
- The newest card sits in the corner, and older ones stack upward. At most 4 are visible; a fifth pushes the oldest out, and that one stays in Recent Captures.
- The stacking, the fade and hover states, and the click-vs-drag rule are pure and tested.

**Filmstrip.** One at a time.
- A horizontally scrolling row of frames above the cards, each with its caption.
- ✕ on hover removes a frame: it dims and offers Restore. The last remaining frame can't be removed.
- Single frames can be dragged out.
- ✕, Esc, a click outside it, or a click on the card closes it and applies the removals (§6).

**Session 4's menu and permissions**
- The menu has Start/Stop Recording, Recent Captures ▸ (the last 5, found by scanning for `.flipbook`), Open Captures Folder, and Quit.
- The icon shows idle or recording.
- At launch, any missing permission is requested with the system prompt. The guided first launch comes in Session 5.

**The Settings model.** It's built in Session 4 because the recording code reads it.
- A typed value over `UserDefaults`, with spec §3.6's defaults, tested for defaults and clamping.
- Advanced ranges:
  - hold threshold: 150–500 ms;
  - reveal: at least the hold threshold + 200 ms, up to 1500 ms;
  - double-tap window: 200–500 ms.
- A change applies to the next recording. A new trigger key or new gesture timings apply as soon as Flipbook is idle.

**Sounds:** Tink to start and Pop to stop, at reduced volume. Neither plays on discard or cancel.

## 8. App, part 2 (Session 5): Settings, picker, first launch, menu

**Settings window.** SwiftUI, with the tabs from spec §3.6: General, Record, Output, Permissions, Advanced.
- It opens from the menu, and Flipbook stays menu-bar-only while it's open.
- Permissions shows each permission's live status, with Open System Settings.
- The fn note adds that some third-party keyboards never send fn to macOS.

**Record tab: the Meet-style picker**
- **Entire screen:** a "Screen with the cursor" tile, plus one thumbnail per display.
- **Window:** a thumbnail grid of open windows, each with its app icon and title.
- Thumbnails are captured when the tab opens (`SCScreenshotManager`). Without Screen Recording, the tab shows the permission row instead.
- The choice sticks. A window choice lasts as long as that window exists.

**First launch: one checklist window**
- Three rows: Screen Recording, Input Monitoring, Accessibility. Each row has one sentence on why, a button, and a live ✓.
  - The first press of a button shows the system prompt. Later presses open the matching System Settings pane.
- Screen Recording and Input Monitoring only apply after a relaunch (M0). So once either button has been pressed, a **Quit & Reopen** button appears, and the window reopens where it left off.
- The last row says "Double-tap Right ⌘ to try it", naming whichever trigger is set. The first recording closes the window.
- The window can be closed at any time. Flipbook works with whatever was granted.

**Launch at login**
- It's registered on first launch (`SMAppService.mainApp`), but only when Flipbook runs from `/Applications` or `~/Applications`. Otherwise General says to move Flipbook there.
- If the status is "requires approval", Settings points to Login Items.

**The full menu**
- **Fix permissions…** at the top, shown only when a permission is missing. It opens the checklist.
- Start/Stop Recording, Recent Captures ▸, Open Captures Folder, Settings…, Quit.
- The icon is an SF Symbol template, tinted red while recording. There's no Dock icon.

**The rest**
- The Sounds toggle and the Save raw sessions toggle (Advanced).
- The retention schedule.
- Deleting `spikes/` and its Makefile targets.

## 9. Testing, self-test, log

**Unit tests.** Test-first, run with `make test`.
- **Core:**
  - M1's 118 tests;
  - `LiveSession`: order, slots, timeouts, ticks, stop, frames after stop;
  - the writer round trip;
  - the live-equals-replay property;
  - the cursor rules.
- **Capture:** sizing, signatures from synthetic pixel buffers, dirty rects, point mapping, the cursor box, the target fallback, and the status-item exclusion plan over fake window lists.
- **Input:**
  - trigger keys and key classification over synthetic `CGEvent`s, with the keyboard layout injected;
  - shortcut names, the scroll fraction, dropping events outside the recorded area;
  - AX label rules over a fake element tree, including that a secure field's value is never read;
  - Chrome/Electron detection.
- **Export:** the folder store, collisions, crash leftovers, rendering sizes and pixel probes, marker numbering and clipping, the PNG round trip, trims, retention, and cleanup after a failed write.
- **App:** `SessionController` with fakes, the pill text, card stacking, fade and click-vs-drag, Recent Captures, settings clamping, and the checklist's row states.
- **Not unit-tested:** the stream setup, event taps, AX calls, panel drawing, SwiftUI views, and `SMAppService`. The self-test and the checkpoints cover these.

**The self-test** (`make selftest`)
- It runs `Flipbook --selftest <dir>` through `open -W -n`, so macOS treats it as the app itself.
- In this mode the app requests no permissions, installs no taps, and shows no menu-bar icon.
- It opens a normal test window that plays a scripted scene of about 9 s, with its own drawn pointer (the stream hides the real cursor). A dialog opens, a checkbox ticks under a pointer that stays put, text appears in a field, the dialog closes, and a list scrolls.
- It records that window through the real stream, using `currentProcess` content, so no permission is needed. Scripted clicks, keys, and scrolls go into `LiveSession` at the matching times. Then it finishes and exports the normal way.
- It writes `selftest.json` and exits with 0 or 1. The report holds:
  - how many frames arrived (complete and idle), and the time to the first frame;
  - the time spent computing signatures per frame;
  - the captions it picked, compared with what the script expects;
  - the export time, and the time from stop to a draggable card;
  - the files written.
- The agent reads the report and looks at the PNGs, which show only the synthetic scene.
- It exists as soon as the pipeline is wired in Session 4, and runs after every later task that touches capture, export, or the app. Session 5 uses it as a regression check, and Fayzan can run it on the work Mac.
- If no frames arrive because the Mac is asleep or locked, the report says so. The session continues with the unit tests and retries the self-test later.
- If macOS asks for Screen Recording anyway, the session stops and asks Fayzan to grant it once.

**UI snapshots** (`make ui-snapshots`). `Flipbook --render-ui <dir>` draws every panel and window state offscreen to PNGs: the pill, card, filmstrip, Settings tabs, and the checklist. Like the self-test, it needs no permissions, so unattended sessions can look at the UI they build.

**The log.** `~/Library/Logs/Flipbook.log`.
- It records gestures, state changes, capture and export timings, the picker's keep and discard counts, errors, permission status, and what the status-item lookup found.
- It never contains labels, window titles, or keys.
- It's capped at 5 MB, with one rotation.
